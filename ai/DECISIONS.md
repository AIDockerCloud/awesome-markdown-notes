# 架构与技术决策记录 (DECISIONS.md — Lite)

## DEC-001 — 采用「按用途分层 + 四字段可判定」的收录口径

日期: 2026-11-10 | 状态: Accepted
- 确认来源: 仓库作者在 `README.md` 开头「判定基准」与「收录标准与维护方式」两节明文确立，见提交 `788a05c`（2026-11-10）
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当清单需要改为投票 / 星数排序、按单一维度横比，或四字段中出现无法普遍判定的新形态时复审
- 背景 (Context): 现成清单口径各异 —— 有的只收编辑器，有的只收自托管，有的靠用户投票把编辑器、知识库、速记混排，选软件时容易错位。
- 决策 (Decision): 按用途分层收录，不把单文件编辑器、知识库、速记和任务管理混在一张表里比；每条至少判定协议、平台、数据存哪、AI 形态四件事，判定不了只进候选不进正表；同一软件只进一个主分区。人类明确指示的批量转正例外见 DEC-006。
- 理由 (Reason): 迁移成本、数据格式和日常操作完全不同，把不同类型放一起横比会误导；只记可判定字段能避免把宣传语当事实写进清单。
- 备选方案 (Alternatives): 投票型排序（AlternativeTo，全但混排、结论不可靠）；按 GitHub 星数排序（appsgit，只看热度不看用途）；按功能清单逐项打分（维护成本高、易过期）。
- 影响 (Consequences): 清单更克制、可长期验活；代价是不追求「一次收全」，且每条新增都需人工核实四个字段，维护成本高于自动聚合。

## DEC-002 — 上下文管理采用 PCMP Lite 档位

日期: 2026-11-10 | 状态: Accepted
- 确认来源: 用户 2026-11-10 回复「1都接受」，明确接受待确认项 1（DEC-002 / 003 / 004），见 DEC-007
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当项目转为多人协作、出现多阶段交付，或需要会话级审计归档与全文检索时，评估升级为 Full 档位
- 背景 (Context): 项目是单人维护、内容驱动的清单仓库，唯一产物为 `README.md`，无源码、无构建、无测试；但跨会话仍会丢失收录口径与当前焦点。
- 决策 (Decision): 引入 PCMP v2.2 Lite 极简 4 件套（`AGENTS.md` + `ai/PROJECT.md` + `ai/STATE.md` 合并活动任务 + `ai/DECISIONS.md`），并把中英两份协议原版原样复制到根目录；不建 `sessions/`、`ARCHITECTURE.md`、`PLAN.md`、`ISSUES.md`，不引入 `scripts/pcmp_index.py` 派生索引。
- 理由 (Reason): Full 档的会话归档、架构图谱与 SQLite 索引对无代码的清单项目属于治理通胀，维护负担大于收益；Lite 已能覆盖「接管必读 + 硬约束 + 当前焦点 + 决策留痕」四项恢复要求。
- 备选方案 (Alternatives): Full 档（治理成本过高，放弃）；仅在 README 写一段说明、不建 `ai/`（无法按 revision 追踪状态，跨会话仍会失忆，放弃）。
- 影响 (Consequences): 上下文自足、零工具依赖；代价是没有自动化 `--check` 合规校验与会话级审计证据，状态维护依赖 Git 提交说明与人工核对。

## DEC-003 — 采用「主清单 + 分类目录（卡片 + 对比清单）」双层内容结构

日期: 2026-11-10 | 状态: Accepted
- 确认来源: 用户 2026-11-10 回复「1都接受」，明确接受待确认项 1，见 DEC-007
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当卡片与对比表数量增长到人工维护困难、或出现同一信息在两层反复不一致时，评估改为单一真源 + 自动生成
- 背景 (Context): 主清单每条只有一两句话，既看不了单款详情，也看不出一整类产品的总体情况；用户会不定时新增软件，需要一套可扩展、新增成本固定的结构。
- 决策 (Decision): 保留 `README.md` 作为分层主清单；在其下按同一套分类建 `categories/<NN>-<slug>/`，每款软件一张产品卡片、每类一张对比清单（横向对比表 + 本类整体情况 + 进展表）；`categories/_TEMPLATE.md` 作为统一卡片模板；`06-references` 作为外部索引资源不建产品卡片。
- 理由 (Reason): 双层结构让「选品类」与「看单款」各有一处入口，且用户新增软件时只需复制模板 + 在对比表补一行，成本固定；对比表同时充当定时任务的巡检对象清单，避免维护第二份名单。
- 备选方案 (Alternatives): 只扩写主清单条目（一张表会无限变长、无法横向对比，放弃）；用脚本从数据表生成所有 Markdown（引入生成层作为隐含真源，违背「Markdown 权威」原则且新增软件要改代码，放弃）；每款软件单独建站 / 子仓库（维护与导航成本过高，放弃）。
- 影响 (Consequences): 单款与分类视图都可读，新增流程明确；代价是同一事实在两层各出现一次，存在分叉风险 —— 已用硬约束 8「不设双真源：冲突时标记差异并核实来源，不静默覆盖」加以约束。

## DEC-004 — 建立每周轻量核实与进展更新机制

日期: 2026-11-10 | 状态: Accepted
- 确认来源: 用户 2026-11-10 回复「1都接受」，明确接受待确认项 1；调度细节另由 DEC-006 确认改为周六 09:00，见 DEC-007
- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当软件数量增长导致单次核实流量 / 耗时明显上升，或验收发现进展记录频繁失真时，调整频率、分批策略或改为按需核实
- 背景 (Context): 清单自称「价值在持续验活，不在一次收全」，但初版没有验活日期戳、候选区或失效记录；卡片里还有大量「待核实」字段，靠人工定期补齐不现实。
- 决策 (Decision): 建立每周定时任务（初拟周一 09:00，**2026-11-10 起为周六 09:00**），遍历 `categories/*/README.md` 对比表与 `categories/_WATCHLIST.md` 观察名单动态发现检查对象，轻量核实正式 Release、近 6 个月提交、协议变化、归档 / 停更与四字段变化；结果写入根 `CHANGELOG.md`、各分类「进展」表与有实质变化的卡片「进展记录」表；只标注不自动移出条目，不执行 `git commit`。
- 理由 (Reason): 以对比表与观察名单为真源动态发现，用户不定时新增的软件会自动纳入，无需改任务配置；每周频率兼顾「持续验活」与本机蜂窝热点的流量配额，提示词已限制为轻量 HTTP、不 clone、不下载、不反复重试。
- 备选方案 (Alternatives): 每日核实（流量与打扰过高，放弃）；每月核实（条目停更发现太晚，与「持续验活」定位不符，放弃）；CI 里跑自动化脚本抓取（要引入依赖与密钥、违背零依赖定位，放弃）。
- 影响 (Consequences): 进展有稳定写入点与审计线索，待核实字段可逐步补齐；代价是每周产生工作区改动需人类 review，且核实结果受公开页面可得性限制，核实不到时只能记「未核实到」。

## DEC-005 — 融合两个每周定时任务，采用「对比表 + 观察名单」双真源巡检

日期: 2026-11-10 | 状态: Accepted
- 确认来源: 用户 2026-11-10 指示「把现有的这个定时任务和项目定时任务融合下，同时把内容补充进仓库中的更新进展」；同日「删掉旧任务吧」是对融合结果的最终确认。收尾细节由 DEC-006 细化。
- Supersedes: 无
- Superseded-by: 无（收尾变更见 DEC-006）
- 复审触发条件 (Review Trigger): 当检查对象数量使单次核实流量 / 耗时明显上升时，评估是否合并两处真源或改为分批核实
- 背景 (Context): 项目的核实任务以分类对比表为真源，只覆盖已收录的 24 款；另有每周五 18:00 跑的旧任务「笔记软件更新进展」，写死 16 款名单（含 GitHub URL），按「对比上一次」逐周输出报告，已积累 4 份报告与 5 份快照。两个任务部分重叠却各跑一遍，对本机蜂窝热点流量是重复消耗；旧任务的历史基线又只存在其私有工作目录里，仓库看不到。
- 决策 (Decision): 保留项目任务（ID `b7a78148…`）为唯一 ACTIVE 任务，提示词并入旧任务的 16 款名单、「对比上一次」语义、GitHub atom 轻量数据源与状态对照表写入要求；名单落进 `categories/_WATCHLIST.md`；4 份历史报告与 5 份快照的结论回填 `CHANGELOG.md`、7 个分类进展表与 8 张产品卡片，全部标注「历史回填（未联网复核）」。旧任务（ID `581c89c5…`）先 PAUSED、同日按用户指示删除；调度由周一 09:00 改为周六 09:00（DEC-006）。
- 理由 (Reason): 名单落在仓库文件里，既符合「不写死名单」又便于人工维护；合并后每周只跑一次，避免重复抓取；「对比上一次」的基线从旧任务私有目录搬进仓库，跨会话不丢；历史回填全部带来源标注，不冒充本轮核实结论。
- 备选方案 (Alternatives): 保留两个任务各跑各的（重复消耗流量、进展分叉，放弃）；把名单直接写进定时任务提示词（名单写死、不可维护，放弃）；把 4 份历史报告原文复制进仓库（含大量版本号与主观判断，与「只写结构性事实」口径冲突，放弃）；把 8 款候选直接补进正表（当时四字段未判定、无人类授权，后由 DEC-006 授权执行）。
- 影响 (Consequences): 巡检覆盖扩到 32 款且历史基线可追溯；代价是两处真源需人工保持一致（已用硬约束 8 / 13 约束），且历史回填内容须经人类确认后才能当作已核实事实。

## DEC-007 — 人类逐项确认的三项口径收口（ADR 转正 / TypeOpen 保留 / 闭源门槛看官网）

- Supersedes: 无
- Superseded-by: 无
- 复审触发条件 (Review Trigger): 当首轮联网核实发现 TypeOpen 四字段仍无法判定、或官网发布记录也不足以判定闭源产品活跃度时，复审这两条例外口径
- 背景 (Context): 上一轮汇总出 4 类待确认项请人类裁定，用户逐项给出结论；其中「git 未跟踪文件是什么」仅为术语询问，不涉及口径变更，也不授权任何提交动作。
- 决策 (Decision): ① DEC-002 / 003 / 004 全部由 Proposed 转 Accepted，确认来源统一指向本决策；② TypeOpen 四字段缺 3 项，仍**保留在 `01-single-file` 正表**，不转候选，未判定字段继续显式写「—（未核实）」；③ 闭源且无公开仓库的产品（Typora），入选门槛「近 6 个月内有提交」**以官网发布页 / 更新记录判定**，不以 GitHub 提交判定（用 https://typora.io/releases/stable.html，DNS 异常时走官方中文站同页）。

- 影响 (Consequences): DEC-001 ~ 007 全部 Accepted，`STATE.md` 的「阻塞项」清空；01 / 00 两处 [未决] 消除；判定口径写进硬约束 4、AGENTS 红线 3、分类清单、产品卡片与 `_WATCHLIST.md`，并同步定时任务提示词，避免每周重复提出。主清单 `README.md` 的通用门槛表述保持不变，特例只在项目上下文层承载。
